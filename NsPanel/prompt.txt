# Task: Build VPS Admin Panel 

## Project Overview

Build a lightweight web admin panel for managing an Ubuntu VPS. The panel is a **thin UI wrapper** over the attached bash script [ubuntu.sh](ubuntu.sh). The bash script remains the source of truth for installation and site-creation logic; the panel collects inputs via forms and invokes bash functions with arguments. 

The panel runs on the same VPS it manages. It is launched manually when needed (not a persistent systemd service), prints a random password on startup, and listens on localhost only.

## Tech Stack (locked — do not deviate)

- **Backend:** Python 3.11+, FastAPI, Uvicorn (standard, not gunicorn)
- **Templates:** Jinja2 (FastAPI built-in)
- **System info:** `psutil`
- **YAML:** `pyyaml` for site metadata files
- **Frontend:** Tailwind CSS via CDN (dark theme by default), HTMX for partial swaps, vanilla JS where needed. **No build step, no bundler, no npm.**
- **Streaming:** Server-Sent Events (SSE) for live command output. No WebSockets.
- **State:** Filesystem only. No database. Site metadata stored as `info.yml` inside each site directory.
- **Auth:** HTTP Basic Auth, password regenerated on each startup and printed to console.

## Binding & Security

- Bind to `127.0.0.1:7777` ONLY. Never `0.0.0.0`. Hardcode this — no flag to change.
- Operator accesses via SSH tunnel: `ssh -L 7777:localhost:7777 user@server`.
- Random password generated on startup using `secrets.token_urlsafe(16)`, printed to stdout in a prominent banner.
- Username fixed as `admin`.
- All routes (except static assets) require Basic Auth via a single FastAPI dependency.
- Single-user assumption: no session management, no concurrent users, no rate limiting needed.

## Architectural Principles

1. **Bash script is the engine.** The panel collects inputs via forms and invokes bash functions with arguments. No business logic gets re-implemented in Python — only orchestration, status checks, and metadata management.

2. **Bash script bottom dispatcher:** Replace the `main_menu` call at the bottom of `ubuntu.sh` with:
   ```bash
   if [ $# -gt 0 ]; then
       "$@"
       exit $?
   else
       main_menu
   fi
   ```
   So `bash ubuntu.sh install_nginx` or `bash ubuntu.sh add_static_site myapp port 7890` runs the function directly. Bare `bash ubuntu.sh` keeps the original menu.

3. **Status checks happen in Python**, not bash. Use `which`, `systemctl is-active`, `systemctl show -p MainPID`, `dpkg -l`, version flags via subprocess. `psutil` for system metrics.

4. **Idempotency:** Every install action checks status first. If already installed, refuse and show a clear message. Don't even start the subprocess.

5. **Filesystem as truth:** Sites are discovered by scanning `/var/www/nginx/sites/`. Each site has an `info.yml` metadata file written by the bash function when it creates the site. No panel-level state DB.

## Bash Script Modifications

The script has two kinds of changes: **(a) the dispatcher** at the bottom, and **(b) new non-interactive wrapper functions** that the panel calls. Existing interactive functions stay untouched so the script still works standalone.

### New functions to add to `ubuntu.sh`

Add these AFTER the existing functions, BEFORE the menu definition. Each writes `info.yml` to the site directory.

**1. `add_static_site <name> <access_kind> <access_value>`**
- `access_kind`: `domain` or `port`
- `access_value`: domain name or port number
- Creates `/var/www/nginx/sites/<name>/public/`, writes static index.html, writes nginx conf, runs `nginx -t`, reloads nginx, writes `info.yml`.

**2. `add_proxy_site <name> <access_kind> <access_value> <proxy_target>`**
- `proxy_target`: e.g. `http://127.0.0.1:5555` or `http://192.168.1.2:6666`
- Writes nginx conf with `proxy_pass`, reloads nginx, writes `info.yml`.

**3. `add_dotnet_site <name> <access_kind> <access_value> <dll_name> <internal_port>`**
- Creates site dir, downloads sample blank site if needed (same as current logic), renames dll files, writes systemd unit at `/var/www/services/<name>.service`, writes nginx conf proxying to `127.0.0.1:<internal_port>`, enables + starts service, writes `info.yml`.

**4. `install_postgres_remote_auto <db_password>`**
- Non-interactive version of `install_postgres_remote`. Reuses the original by extracting the password-prompt section into a parameterized inner function. Existing interactive function calls this with read input.

### Functions kept unchanged (already non-interactive)

The panel can call these directly with no args:
- `install_nginx`
- `install_netcore`
- `install_mongodb`
- `install_elastic_kibana`
- `install_fail2ban`
- `common_configs`
- `install_virtual_ram_4g`

### info.yml schema (written by bash functions)


```yaml
name: myapp
type: dotnet              # static | proxy | dotnet
created_at: 2026-05-14T10:00:00Z
access:
  kind: port              # domain | port
  value: "7890"           # quote to keep string
backend:
  internal_port: 5555     # null for static
  dll: myapp              # null for static/proxy
  proxy_target: null      # set for proxy type
paths:
  public: /var/www/nginx/sites/myapp/public
  nginx_conf: /var/www/nginx/conf.d/myapp.conf
  systemd_unit: /var/www/services/myapp.service   # null for static
  log_dir: /var/www/nginx/log
```



Bash writes this using a heredoc. Panel only reads it.

## Module Interface

`panel/modules/base.py`:


```python
from abc import ABC, abstractmethod
from typing import Optional

class Module(ABC):
    name: str                    # "nginx"
    display_name: str            # "NGINX Web Server"
    description: str
    bash_function: Optional[str] # "install_nginx", or None

    @abstractmethod
    def is_installed(self) -> bool: ...

    @abstractmethod
    def get_status(self) -> dict:
        """Returns: {installed, version, service_state, ports, extra}"""
        ...
```


`registry.py` auto-imports all .py files in `modules/`, finds `Module` subclasses. Adding a tool = one file.

## Phase 1 Features (MVP — build this, no more)

### 1. Auth
- Single Basic Auth dependency on all routes.
- Username `admin`, password from startup-generated secret.

### 2. Dashboard (`/`) — the main page, must look polished

This is the page operators stare at most. It must be information-dense and visually clean.

**Layout (top to bottom):**

**Section A — System Stats (4 stat cards in a row):**
- CPU: percent + small sparkline if easy, else just %.
- RAM: used / total GB + %.
- Disk: used / total GB for `/` + %.
- Uptime: human-friendly (`5d 3h 22m`).
- Below the row, a thin text line: hostname, kernel version.

**Section B — Sites (a table or stacked cards):**
- Scan `/var/www/nginx/sites/`, read each `info.yml`.
- For each site show: name, type (badge), access (domain or `:port`), service status, PID (if dotnet), last modified.
- Service status logic:
  - `static`: "OK" if `nginx_conf` exists and `nginx -t` passes globally.
  - `proxy`: same as static (panel doesn't probe the upstream).
  - `dotnet`: `systemctl is-active <name>` + `systemctl show -p MainPID <name>` for PID.
- Status badge colors: emerald (running/ok), rose (failed/stopped), amber (configured but unknown), zinc (unknown).
- Each row clickable → `/sites/{name}`.
- A "Create Site" button at the top right of this section.

**Section C — Installed Tools (compact grid):**
- One small card per registered module.
- Each card: tool icon/initial, name, install ✓/✗, service state dot, version (small text if installed).
- Card click → `/tools` (jump to that tool's full card).

**Refresh:** small refresh button per section, or single button at top. No auto-poll in Phase 1.

### 3. Tools (`/tools`)
- Larger grid of cards, one per module.
- Card content: icon, name, description, install status badge, version, service state, "Install" button (if not installed) or "Status" details.
- Install click → POST creates job, opens modal with SSE log stream.
- Idempotency: toast "Already installed" if user clicks install on installed module.

### 4. Sites List (`/sites`)
- Full version of the dashboard sites table (more columns, filters later).
- Same row partial reused (`_site_row.html`).
- "Create Site" button → `/sites/create`.

### 5. Sites Create (`/sites/create`)
- Form with progressive disclosure:
  - Site name (slug, no spaces).
  - Access kind: `domain` | `port` (radio).
  - If domain: text input. If port: number input with "Generate" button (random 5000-50000).
  - Backend type: `static` | `proxy` | `dotnet` (radio).
  - Conditional fields per backend type:
    - static: nothing extra.
    - proxy: target URL.
    - dotnet: dll name, internal port (auto-suggest = access port - 1 if port mode, else random).
- Submit → panel determines which bash function to call (`add_static_site` / `add_proxy_site` / `add_dotnet_site`), invokes with args, streams output via SSE.
- On success, redirect to site detail page.
- On failure, show stream output + error message.

### 6. Site Detail (`/sites/{name}`)
- Full info from `info.yml`.
- Service status panel: state, PID, memory (if dotnet — `psutil.Process(pid).memory_info().rss`).
- Action buttons (each triggers a stream job):
  - Restart Service (dotnet only).
  - Reload Nginx (any).
  - Show Config (modal: contents of `nginx_conf` file).
  - Tail Logs: last 100 lines of nginx access + error logs (and systemd journal for dotnet).
- Delete button: placeholder, disabled with "Phase 2" tooltip.

### 7. Live Log Stream
- SSE endpoint `GET /stream/{job_id}`.
- Job created when user triggers install / site-create / restart.
- `core/runner.py` provides an async generator that runs a subprocess, yields stdout/stderr lines as SSE events.
- Frontend `static/js/sse.js` uses `EventSource`, appends each line to `<pre>`, auto-scrolls.
- Strip ANSI codes server-side.
- Send final event with exit code, then close.
- Job state in-memory dict. Lost on panel restart — acceptable.

### 8. Audit Log
- `core/audit.py` exposes `log(action, detail)`. Appends `ISO8601 | action | detail`.
- Logged on: install attempt, site create/restart/reload, login.
- `/logs` page shows last 200 lines, newest first.

## UI/UX Specifics

- **Dark theme always on.** `<html class="dark">` hardcoded. No toggle in Phase 1.
- Palette: zinc/slate base, emerald-500 success, rose-500 danger, amber-500 warning, sky-500 info.
- Sidebar nav: Dashboard, Tools, Sites, Logs, (Settings placeholder, disabled).
- Status badges: colored dot + label via `_status_badge.html` partial.
- Stat cards: large number, label below, subtle gradient or border, all consistent via `_stat_card.html`.
- Log stream: `bg-black`, `font-mono text-sm`, max-height with overflow, auto-scroll.
- Toast: top-right, auto-dismiss 3s.
- HTMX: section refresh on dashboard, site action buttons, status re-check on tool cards.

## Constraints (do NOT do)

- Do NOT use React, Vue, Svelte, or any frontend framework.
- Do NOT use a database (no SQLite).
- Do NOT use WebSockets — SSE only.
- Do NOT bind to `0.0.0.0`.
- Do NOT bundle Tailwind — CDN only.
- Do NOT re-implement site creation or install logic in Python — call the bash functions.
- Do NOT pipe stdin to bash functions to fake interactive input — use the new param-accepting functions.
- Do NOT add features beyond Phase 1. Leave `# TODO Phase 2` comments where useful.
- Do NOT add tests beyond a minimal smoke test that imports the app.
- Do NOT add DI frameworks, factories, deep abstraction.
- Do NOT add pydantic models for things that don't cross a serialization boundary.

## Working Style

- Build incrementally. Order: bash function rewrites → auth → dashboard skeleton → system stats → sites scan → one tool install end-to-end → site create.
- Test each layer before moving on. Don't write 30 files then try to boot.
- Keep functions short. Prefer flat code over abstraction.
- Comments only where logic is non-obvious. No docstrings for trivial functions.
- Match existing bash directory and naming conventions exactly.
